# Fixtures модуля matching (C)

Тестовые данные для разработки и демонстрации модулей **matching** и **fsp**. Все кандидаты, компании и достижения ФСП — вымышленные. Данные используются как в коде (сид БД), так и для ручного демо.

Все файлы — валидный JSON. Форматы приближены к контрактам из `План-разработки-ФСП-Сигнал.md` часть III и могут потребовать небольшой адаптации под итоговые Pydantic-схемы.

## Содержимое

| Файл | Что лежит | Записей |
|---|---|---:|
| `skills.json` | Справочник проверяемых навыков | 7 |
| `categories.json` | Специализации, грейды, активные категории | 2 + 3 + 6 |
| `companies.json` | Профили компаний-работодателей | 3 |
| `needs.json` | Описания потребностей компаний (вакансии) | 3 |
| `candidates.json` | Карточки кандидатов с тестами, навыками и ФСП | 15 |

Статусы ФСП: 9 с достижениями (`linked_with_data`), 5 без связи (`not_linked`), 1 с ошибкой адаптера (`unavailable`). Это даёт покрытие всех веток UI и критичную проверку: сильные кандидаты без ФСП (К027, К094) могут оказываться в выдаче выше кандидатов с достижениями.

## Пограничные случаи для демо и тестов

Эти кандидаты специально оставлены, чтобы показать корректное поведение системы:

- **К041** (`publication_consent=false`) — отозвала публикацию. Не должна появляться в выдаче и обновлённых снимках поиска, даже если была в избранном.
- **К072** (`email_verified=false`) — не прошла подтверждение. Не должна быть `discoverable`, в выдачу не попадает.
- **К109** (`fsp.status=unavailable`) — адаптер ФСП временно недоступен. UI должен показать особое состояние, не путая его с отсутствием достижений.
- **К123** (`declared_grade=middle`, `verified_grade=junior`) — заявляла Middle, не прошла, добровольно подтвердилась Junior. Проверка правила «грейд не понижается принудительно».
- **К027** (сильный тест, нет ФСП) — должна опережать кандидатов с ФСП в выдаче при одинаковом соответствии. Защищает от обвинения «ФСП подменяет компетентность».
- **К003** (`результат теста 78`, FSP победитель + призёр) — наоборот, два ФСП-достижения не должны вывести его выше К014 (`результат теста 86`, FSP финалист) при одинаковой релевантности.

## Формула подборки для подсчёта

Начальная предлагаемая формула из плана:

```
score = 0.65 * T + 0.25 * R + 0.10 * F
```

- `T` — балл последнего теста (0–100)
- `R` — взвешенное соответствие проверенных навыков задачам работодателя
- `F` — ограниченный сигнал достижений ФСП (участник=30, финалист=60, призовое=85, победитель=100)

Для общего банка без потребности: `score = 0.90 * T + 0.10 * F`.

## Загрузка в разработке

Для быстрой итерации рекомендуется писать небольшой скрипт на Python, который читает эти файлы и наполняет БД через существующие SQLAlchemy-модели (когда они появятся). Пока модели не готовы — файлы читаются напрямую из эндпоинтов `matching/router.py`.

Пример минимальной функции (пригодится в `apps/api/app/modules/matching/service.py`):

```python
from pathlib import Path
import json

def load_candidates():
    path = Path(__file__).resolve().parents[4] / "fixtures" / "matching" / "candidates.json"
    return json.loads(path.read_text(encoding="utf-8"))["candidates"]
```

## Что НЕ в этих fixtures

- Пароли и реальные контакты — не кладутся. Email в формате `*@signal.test` — служебные.
- Личные документы, фото, резюме как файлы — не моделируем.
- История приглашений и ContactGrant — это модуль D, его фикстуры будут отдельно.
- Расширенные ветки опроса и результаты тестирования — модуль B, его фикстуры отдельно.

## Обновление файлов

Если нужно добавить/изменить кандидата:

1. Сохраняем формат, не ломаем валидный JSON.
2. UUID кандидата — следующий свободный в серии `10000000-0000-4000-8000-000000000XXX`.
3. Обновляем `updated_at` на дату изменения.
4. Если меняется поведение демо — отражаем в этом README.
