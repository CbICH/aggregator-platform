# Блок C: подборка кандидатов для работодателя

## Что реализовано

- Профиль компании работодателя (`companies`): создание, чтение, частичное обновление. Один владелец — одна компания; попытка повторного создания отвергается кодом `COMPANY_EXISTS`. Создание компании автоматически заполняет `users.company_id`.
- Потребности компании (`employer_needs`): название, описание, специализация, список допустимых грейдов, декларируемый стек, набор требуемых навыков с весами 1–5, формат работы, диапазон зарплаты. Валидация запрещает перевёрнутый диапазон и пустой список требуемых навыков.
- Демонстрационная подборка синтетических кандидатов с объяснимым скорингом: формула меняется в зависимости от того, выбрана ли конкретная потребность. Без потребности выдача упорядочена по тесту и ФСП, с потребностью добавляется релевантность проверенных навыков требуемым.
- Карточка кандидата показывает балл, разложение по компонентам, список подтверждённых навыков с баллами и машиночитаемые причины: `GRADE_VERIFIED`, `SKILL_MATCH`, `SKILL_NOT_ASSESSED`, `FSP_SIGNAL`, `FSP_UNAVAILABLE`.
- Справочник категорий `/employer/categories` возвращает шесть категорий и количество видимых кандидатов в каждой; категории с `active=false` остаются в ответе с нулевым счётчиком и не фильтруются из выдачи.
- Банк из 15 фикстурных кандидатов (6 специализация/грейд, разнородные стеки и статусы ФСП) обеспечивает демо-выдачу и покрывает граничные случаи: отсутствие согласия на публикацию, неподтверждённый email, недоступный ФСП, расхождение заявленного и подтверждённого грейда, сильный тест без ФСП и слабый тест с победой ФСП.

## API

| Метод | Назначение |
|---|---|
| `POST /api/v1/company` | Создать профиль компании владельца |
| `GET /api/v1/company` | Получить профиль собственной компании |
| `PATCH /api/v1/company` | Частично обновить профиль собственной компании |
| `POST /api/v1/employer/needs` | Создать потребность в рамках собственной компании |
| `GET /api/v1/employer/needs` | Получить список потребностей собственной компании |
| `GET /api/v1/employer/needs/{need_id}` | Получить одну потребность собственной компании |
| `GET /api/v1/employer/categories` | Получить справочник категорий с количеством кандидатов |
| `GET /api/v1/employer/matching/candidates` | Получить демонстрационную отсортированную подборку кандидатов из C-фикстур |

Live-выдача опубликованных профилей D остаётся на `GET /api/v1/employer/candidates`; маршруты намеренно разделены, чтобы синтетические карточки C не подменяли privacy-проверки D.

Все методы требуют подтверждённую роль работодателя, сессию и CSRF-заголовок на изменяющих. Параметры `/employer/matching/candidates`: `specialization`, `grade`, `with_fsp_only`, `need_id`, `limit` (1..50, по умолчанию 20). Указание `need_id` переопределяет ручные фильтры по специализации и грейду — они берутся из потребности. Чужая потребность или несуществующий `need_id` возвращают `404 NEED_NOT_FOUND`, не раскрывая данные другого работодателя.

## Формула подборки

Балл кандидата рассчитывается на бэкенде, нормирован к 0..100 и округлён до одного знака после запятой.

Без потребности:

```
score = 0.90 * T + 0.10 * F
```

С потребностью:

```
score = 0.65 * T + 0.25 * R + 0.10 * F
```

- `T` — поле балла теста синтетического кандидата (0..100). В текущем демо читается из JSON-фикстуры; для живого подбора необходимо подключить `AssessmentRead` блока B.
- `R` — взвешенное соответствие проверенных навыков требуемым: `R = sum(weight_i * confirmed_score_i) / sum(weight_i)`. Непроверенный требуемый навык даёт 0, но помечается кодом `SKILL_NOT_ASSESSED` — не как «кандидат не умеет», а как «не проверялось тестом».
- `F` — нормированный сигнал ФСП из статуса привязки и лучшего достижения: `участник=30`, `финалист=60`, `призёр/призовое место=85`, `победитель=100`. Статусы `not_linked`, `linked_empty` и `unavailable` дают `F=0`; `unavailable` дополнительно помечается в причинах.

Веса зафиксированы в `app/modules/matching/service.py` как константы `WEIGHT_*`.

## Фикстуры

Исходные данные подборки — JSON-файлы в каталоге `fixtures/matching/`, копируемые в контейнер Dockerfile'ом API в `/app/fixtures-matching/`. Путь разрешается в `app/modules/matching/fixtures.py` поочерёдным перебором двух глубин: контейнер и локальная разработка.

| Файл | Назначение |
|---|---|
| `candidates.json` | Банк кандидатов: `candidate_id`, `display_name`, `specialization`, `verified_grade`, `category_code`, `experience_years`, `work_format`, `declared_stack`, `skills[]`, `assessment.test_score`, `fsp.status`, `fsp.achievements[]`, флаги `publication_consent` и `email_verified`. Невидимые кандидаты (без согласия или без подтверждённого email) исключаются функцией `visible_candidates`. |
| `companies.json` | Демо-компании с фиксированными UUID `40000000-0000-4000-8000-00000000000X`. |
| `needs.json` | Демо-потребности с фиксированными UUID `30000000-0000-4000-8000-00000000000X`. |
| `skills.json` | Каталог проверяемых навыков с префиксами по специализации (`api.*`, `data.*` — backend; `qa.*` — qa). |
| `categories.json` | Шесть категорий: `backend junior/middle/senior`, `qa junior/middle/senior`, с флагом `active`. |

Фикстуры читаются `@lru_cache`, повторная загрузка в рамках процесса не происходит.

## Интеграционный контракт

Модуль C не владеет моделями блоков B и D. Текущий ranking читает банк из JSON-фикстур. Реальные ProfileRead D и AssessmentRead B предоставлены composition root, но ranking их ещё не использует. Подключён только адаптер сигнала ФСП:

- `app.state.assessment_read_factory(db): AssessmentRead` — доступный порт блока B, который пока используется D. Метод `get_verified(candidate_id)` возвращает реальную подтверждённую категорию и балл; подключение этого порта к рейтингу C остаётся задачей интеграции.
- `app.state.fsp_provider: FspProvider` — порт блока C. Метод `get_signal(candidate_id) -> FspSignal` возвращает статус привязки и нормализованный список достижений. Текущая реализация `DemoFspProvider` (`app/modules/fsp/provider.py`) читает те же фикстуры кандидатов. Для другого источника `DemoFspProvider` можно заменить совместимым адаптером в `create_app`; конкретного `HttpFspProvider` сейчас нет. сервис подборки `rank_candidates` принимает провайдер параметром и не содержит ссылок на источник данных. Fallback-провайдер в сервисе существует для юнит-тестов, в проде всегда задействуется зарегистрированный в `app.state`.

Сессия БД пробрасывается стандартной зависимостью `get_db`; собственные модели C — `Company` и `EmployerNeed` — изолированы в `app/modules/matching/models.py` и не экспортируются в контракты.

## Миграции

Миграции C и общий merge Alembic:

- `0009_matching_companies` — таблица `companies` с unique constraint и отдельным индексом по `owner_user_id`; FK к `users.id` использует `CASCADE`.
- `0010_matching_needs` — таблица `employer_needs` с FK к `companies.id` на удаление через `CASCADE` и индексом по `company_id`.

После интеграции с D ревизии `0010_matching_needs` и `0011_assessment_survey_index` соединяет `0012_merge_matching_needs` без DDL. Исходные ID миграций сохранены. Миграции автоматически применяются entrypoint-ом API; пять исходных состояний SQLite и upgrade/check/откат нового head на временной PostgreSQL проверены локально.

## Фронтенд

Модуль `apps/web/src/features/matching/index.tsx` экспортирует манифест `FeatureModule` с четырьмя страницами и тремя пунктами навигации для роли `employer`:

| Путь | Роль | Назначение |
|---|---|---|
| `/employer/company` | employer | Профиль компании: создание и правка через PATCH |
| `/employer/needs` | employer | Список потребностей с переходом в подборку по каждой |
| `/employer/needs/new` | employer | Форма потребности с чекбоксами навыков из каталога и весами 1–5 |
| `/employer/matching/candidates` | employer | Демо-подборка с селектором потребности, фильтрами и разложением балла |

Выбор потребности в селекторе страницы кандидатов читается из URL-параметра `?need=<uuid>` и отключает ручные фильтры по специализации и грейду, которые теперь задаются потребностью. Карточка кандидата при активной потребности показывает четырёхколоночную сетку компонент: `тест`, `соответствие`, `ФСП`, `стек`.

## Проверка

Ручная проверка демонстрационной выдачи повторяема по фикстурному банку: при потребности «Развитие API заказов» (Backend Middle, `api.idempotency` вес 2 + `data.sql` вес 1) первая карточка — кандидат 014 с баллом 82.2, разложение `0.65 × 86 + 0.25 × 81 + 0.10 × 60 = 82.15 → 82.2`.

После объединения 9 октября пройдены 131 API-тест на SQLite и PostgreSQL. Интеграционный тест проверяет сохранённую потребность, ownership и приглашение D с need_id. Отдельная Chromium-проверка проходит регистрацию/компанию/форму потребности/демо-рейтинг/рабочий каталог D. Независимая проба подтверждает: живой опубликованный кандидат D отсутствует в демо-банке C, а ID фикстуры получает 404 в D. Общий live-ranking этими проверками не подтверждён.

## Ограничения прототипа

- `DemoFspProvider` подменяет реальный ФСП фикстурами. Контракт порта `FspProvider` не меняется при переходе на HTTP-реализацию, но интеграционная работа (аутентификация, лимиты, кэширование) остаётся за финальным спринтом. UI связи ФСП ID D пока получает 404, потому что C backend endpoints не добавлены.
- Веса `0.65 / 0.25 / 0.10` зафиксированы в коде как гипотеза MVP. Пересмотр требует валидационного сценария и согласования с A и B.
- Сохранение подборок (snapshots) и избранное работодателя не реализованы — работодатель видит всегда актуальный расчёт, но не историю.
- Демо-карточки C пока не используют разрешённую проекцию ProfileRead D. Контакты реальных кандидатов остаются за портом `ContactAccess` D; ID демо-профиля не позволяет получить доступ к реальному кандидату.
- Фильтр по стеку отсутствует. Отдельного фильтра category_code нет; специализация и грейд выбираются раздельно. Уточнение меняет текущую выдачу, предыдущая подборка не сохраняется.
- На рейтинговой карточке нет действия отправки приглашения D. Живой каталог D предоставляет это действие, но не имеет скоринга C.

## Резерв C11

Резерв использован на вынос источника ФСП в адаптер `FspProvider` (ранее `fsp_signal` обращался напрямую к `candidate.fsp` фикстуры) и на вынос расчёта релевантности с машиночитаемыми причинами в отдельную функцию с покрытием случая «не проверялся в тесте». Объём эндпоинтов и фикстур не сокращался.
