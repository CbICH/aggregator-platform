# Блок C: подборка кандидатов для работодателя

## Что реализовано

- Профиль компании работодателя (`companies`): создание, чтение, частичное обновление. Один владелец — одна компания; попытка повторного создания отвергается кодом `COMPANY_EXISTS`. Создание компании автоматически заполняет `users.company_id`.
- Валидация полей на входе: `trim_fields` в `CompanyCreate` стрижёт пробелы по краям; `required_fields_cannot_be_cleared` в `CompanyUpdate` запрещает отправлять `null` в обязательных полях (поле нужно либо изменить, либо не отправлять совсем).
- Сериализация `Company → CompanyResponse` через `response(company)` подставляет UTC в `created_at`/`updated_at`, если БД вернула naive datetime (SQLite в тестах).
- Эндпоинт подборки `GET /employer/candidates` с объяснимым скорингом: формула и веса сохранены в сервисе; источник кандидатов — живая БД профилей блока D — подключается следующей итерацией. Пока сервис возвращает пустой список, чтобы интеграционный сценарий `B/C/D` видел корректный контракт.
- Детальные эндпоинты одного кандидата (`/employer/candidates/{candidate_id}`) и его контактов (`/employer/candidates/{candidate_id}/contacts`) обслуживаются модулем D (`app.modules.invitations.router`), поскольку живут в privacy/invitation-потоке и используют порт `CompanyRead` блока C (`app.modules.matching.read.SqlAlchemyCompanyRead`).
- Порт `FspProvider` (`app.modules.fsp.provider`) — абстракция источника сигнала ФСП. Текущая реализация `DemoFspProvider` читает фикстуры; в проде подменяется на `HttpFspProvider` в одной строке `create_app`.

## API

| Метод | Назначение |
|---|---|
| `POST /api/v1/company` | Создать профиль компании владельца |
| `GET /api/v1/company` | Получить профиль собственной компании |
| `PATCH /api/v1/company` | Частично обновить профиль собственной компании |
| `GET /api/v1/employer/candidates` | Получить отсортированную подборку опубликованных кандидатов |

Детальные эндпоинты кандидата принадлежат блоку D и описаны в `docs/module-D.md`.

Все методы требуют подтверждённую роль работодателя, сессию и CSRF-заголовок на изменяющих. Параметры `/employer/candidates`: `specialization`, `grade`, `with_fsp_only`, `limit` (1..50, по умолчанию 20).

## Формула подборки

Балл кандидата рассчитывается на бэкенде, нормирован к 0..100 и округлён до одного знака после запятой.

Без потребности:

```
score = 0.90 * T + 0.10 * F
```

С потребностью (планируется):

```
score = 0.65 * T + 0.25 * R + 0.10 * F
```

- `T` — балл последней подтверждённой попытки теста кандидата (0..100), читается из порта `AssessmentRead` блока B.
- `R` — взвешенное соответствие проверенных навыков требуемым: `R = sum(weight_i * confirmed_score_i) / sum(weight_i)`. Непроверенный требуемый навык даёт 0, но помечается кодом `SKILL_NOT_ASSESSED` — не как «кандидат не умеет», а как «не проверялось тестом».
- `F` — нормированный сигнал ФСП из статуса привязки и лучшего достижения: `участник=30`, `финалист=60`, `призёр/призовое место=85`, `победитель=100`. Статусы `not_linked`, `linked_empty` и `unavailable` дают `F=0`; `unavailable` дополнительно помечается в причинах.

Веса зафиксированы в `app/modules/matching/service.py` как константы `WEIGHT_*`. Функция релевантности `relevance()` и нормализация `fsp_score()` реализованы и покрыты сервисом; подключение к источнику кандидатов планируется в отдельном коммите после согласования формата с D.

## Интеграционный контракт

Модуль C не владеет моделями блоков B и D. Внешние данные получаются только через read-only порты и адаптеры из `app.state`:

- `app.state.assessment_read: AssessmentRead` — порт блока B (инстанс для прода).
- `app.state.assessment_read_factory: Callable[[Session], AssessmentRead]` — фабрика для тестов блока D с кастомной `session_factory`.
- `app.state.company_read_factory: Callable[[Session], CompanyRead]` — публичный порт C для чтения потребностей компании (используется D в invitation-потоке).
- `app.state.fsp_provider: FspProvider` — порт блока C для сигнала ФСП; текущая реализация `DemoFspProvider`.

Сессия БД пробрасывается стандартной зависимостью `get_db`; собственные модели C — `Company` — изолированы в `app/modules/matching/models.py` и не экспортируются в контракты.

## Миграции

Единая последовательность ревизий Alembic:

- `0009_matching_companies` — таблица `companies` с уникальным индексом по `owner_user_id` и FK к `users.id`.
- `0010_merge_bcd` — merge-ревизия блока D, объединяющая историю ассессмента B и профилей D.
- `0011_assessment_survey_index` — индекс по опросам блока B.

Миграции применяются автоматически entrypoint-ом контейнера API (`alembic upgrade head && uvicorn`).

## Фронтенд

Модуль `apps/web/src/features/matching/index.tsx` экспортирует манифест `FeatureModule` с двумя страницами и двумя пунктами навигации для роли `employer`:

| Путь | Роль | Назначение |
|---|---|---|
| `/employer/company` | employer | Профиль компании: создание и правка через PATCH |
| `/employer/candidates` | employer | Подборка кандидатов с фильтрами и разложением балла |

## Ограничения прототипа

- Источник кандидатов для `/employer/candidates` переключён с демо-фикстур на БД (профили блока D с `publication_enabled && discoverable && verified_category`). Прошитый обход БД — следующая итерация; пока сервис возвращает пустой список.
- `/employer/needs` (создание потребностей работодателем) выпилен из текущей ветки. Решение по возврату функции и её места в потоке `candidate → invitation` — после согласования с D.
- Веса `0.65 / 0.25 / 0.10` зафиксированы в коде как гипотеза MVP. Пересмотр требует валидационного сценария и согласования с A и B.
- Сохранение подборок (snapshots) и избранное работодателя не реализованы.
- Контактные данные кандидата доступны только через invitation-поток блока D (`/employer/candidates/{candidate_id}/contacts`).

## Резерв C11

Резерв использован на вынос источника ФСП в адаптер `FspProvider`, вынос расчёта релевантности с машиночитаемыми причинами в отдельную функцию и на интеграцию со слоем приватности и приглашений блока D (переход от фикстур к БД-источнику).
