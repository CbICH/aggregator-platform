# ФСП Сигнал: сопроводительная документация блока D

Срез реализации: 10 октября 2026 года. Ответственность D — профиль кандидата, приватность и согласия, адресные приглашения, контактные права, PDF и интерфейсы. В локальной ветке D объединены работы B/C/D и закрыты прежние интеграционные недочёты ФСП, live-подбора, фильтров, истории и перехода из потребности к приглашению.

## Поведение продукта

Кандидат вручную заполняет ФИО, роли, стаж, технологии, софт-скиллы, опыт и контакты. Первое сохранение требует отдельного согласия на обработку профиля. Версия защищает от перезаписи устаревшей вкладкой. Контактный адрес хранится отдельно от адреса входа.

Публикация и видимые поля задаются отдельно. Публичная карточка содержит alias, подтверждённую категорию B и разрешённые роли/стек/стаж. ФИО, резюме и контакты приватны, скрытые поля передаются как null. Профиль доступен при подтверждённом email, полноте, активных согласиях и подтверждённой категории B. История ФСП не обязательна.

Кандидат связывает собственный demo-ФСП ID, видит состояние и серверные достижения либо пустую историю. Чужой ID или клиентский балл не принимаются. Реестр явно синтетический: это разрешённые ТЗ собственные данные, а не интеграция с реальной базой Федерации. При недоступности реестра ranking продолжает работать, удалить связь можно.

Работодатель сохраняет компанию и потребность, получает реальную live-подборку по публичным D-профилям и результатам B. Доступны специализация, грейд, категория, стек и наличие достижений. Score объясняется компонентами теста, релевантности навыков и ФСП. История позволяет вернуться к исходным UUID кандидатов, перечитывая актуальную приватность.

Кнопка приглашения открывает форму с условиями потребности. Предложение без вакансии содержит задачи, зарплату от–до в рублях в месяц gross, компанию, способ связи и реальные основания B. Сервер проверяет владельца потребности и доступность кандидата. Снимок условий неизменяем.

Кандидат видит условия до общения и принимает либо отклоняет. Принятие требует явного разрешения передать контакты конкретной компании. Контактное право атомарно создаётся только при принятии; другая компания доступа не имеет. Отзыв закрывает grant, повтор accept его не возвращает. Скрытие исключает профиль из новых и сохранённых подборок, прежние приглашения сохраняются.

Личный многостраничный PDF содержит кириллицу, контакты владельца, резюме, категорию B и FSP-состояние/достижения. Он выдаётся только самому кандидату при действующем согласии обработки. Noto Sans поставляется в образе под SIL OFL 1.1.

## Архитектура и защита

FastAPI, SQLAlchemy/Alembic/PostgreSQL; React/TypeScript/Vite. A предоставляет Argon2id, серверные сессии, CSRF, Origin и подтверждение email. DTO и OpenAPI экспортируются автоматически, клиентские типы генерируются из OpenAPI.

candidate_id равен UUID пользователя. Контакты выделены отдельно. D предоставляет ProfileRead и ContactAccess; B — AssessmentRead; C — CompanyRead/FspRead. Все read-адаптеры используют Session текущего запроса. Новый единый head 0013_fsp_searches добавляет связь ФСП и историю поиска поверх сохранённой миграционной истории B/C/D. Применённые ревизии не переписываются.

Финал приглашения, событие, согласие и grant сохраняются одной транзакцией. Write-lock профиля и условный UPDATE защищают решения/отзыв на PostgreSQL и SQLite. Idempotency-Key уникален в компании; повтор возвращает прежнюю запись, другое содержание — 409. Частичный unique index ограничивает активное приглашение, сервер ограничивает новые отправки до 30 в час. Audit хранит действие/UUID/request ID без контактов и резюме. Ответы защищены no-store; ошибки не возвращают приватный ввод.

## Проверки

149 API-тестов прошли на SQLite и PostgreSQL. Проверены права/CSRF/изоляция, согласия/отзыв, версии и скрытые поля, salary, snapshots, лимиты/idempotency, конкуренция решений, contacts/grants, Unicode PDF. Новые тесты FSP проверяют владение и четыре состояния, matching — реальные B/D, формулу, фильтры, историю и повторную приватность.

Четыре production Chromium-сценария прошли на Docker/PostgreSQL/Mailpit. Главный сценарий: регистрация/email → профиль → demo-ФСП → реальный тест B → компания/потребность → live-ranking/история → приглашение → принятие/контакты/отзыв → скрытие и unlink. Отдельный подробный D E2E проверяет двух работодателей, отказ и PDF с контролируемыми B/C ports.

Шесть исходных состояний SQLite обновляются с сохранением существующих данных и проходят Alembic check. Временная PostgreSQL прошла upgrade/check/downgrade core/upgrade/check. Runtime head 0013 и check подтверждены. Ruff/формат, контрактная генерация, TypeScript typecheck и production build прошли.

Нагрузочная проверка небольшого стенда: 20 параллельных клиентов одной сессии, 120 чтений каталога/подбора/истории, 7 видимых кандидатов, все HTTP 200; p50 317 мс, p95 431 мс. Это не оценка большой базы. Почта через локальный SMTP Mailpit, подтверждение и вход проверены.

## Запуск и демонстрация

Из корня: cp .env.example .env, затем python3 scripts/dev.py. Приложение localhost:8080, письма localhost:8025, Swagger localhost:8080/api/docs. Вымышленные аккаунты подтверждаются через Mailpit; для внешней почты задаётся настоящий SMTP с TLS в локальном .env. Реквизиты в Git не включаются. Docker down без -v сохраняет данные.

Демонстрационные FSP-аккаунты: demo-fsp-winner@example.com, demo-fsp-finalist@example.com, demo-fsp-empty@example.com; повторный уникальный вариант demo-fsp-winner+метка@example.com. Для остальных аккаунтов создаётся пустой собственный demo-ID. Подробный путь и команды проверок: docs/handoff-D.md; формула: docs/matching.md; FSP: docs/fsp.md; матрица: docs/requirements-D.md.

## Границы сдачи

Обязательный P0 D и его сквозная интеграция завершены локально. Удалённый CI нового изменения подтверждается только после публикации. Внешний реестр/Keycloak, полевой пилот валидности тестов B, публичное размещение и презентация всей команды — отдельные результаты. Необязательные MVP-функции вакансий/откликов/ATS/распознавания PDF не включены. Сдачные материалы D подготовлены как часть общего решения.
