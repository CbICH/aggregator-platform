# Передача D и демонстрация

## Подготовлено

Локальная реализация D: профиль, публикация/скрытие, согласия, публичные проекции, приглашения/статусы/события, контакты, отзыв, PDF и UI ФСП. Схемы в `contracts/`, TypeScript актуален. Ветка локальная; push и PR без команды владельца не выполняются. Сопроводительная документация D: [PDF](D-report.pdf) и [исходный Markdown](D-report.md). Перегенерация: `.venv/bin/python scripts/export_d_document.py`.

## Что подключают A/B/C

1. B: реальный `AssessmentRead.get_verified`, UUID пользователя как candidate_id, категория/skills/test snapshot.
2. C: текущий `User.company_id`, реальный CompanyRead/owns_need, company/need FK отдельной общей миграцией.
3. C: поиск использует `app.state.profile_read_factory(db)`, только публичные поля; сохранённые подборки проверяются заново.
4. C: ФСП endpoints и `FspRead`, подтвердить DTO `fsp_id`/ownership со своей реализацией.
5. A: установить фабрики реальных портов в composition root с одной request Session, выполнить весь настоящий сценарий ниже и CI после публикации ветки.

Все передаваемые даты содержат timezone, включая `FspEvidence.fetched_at`; при чтении naive SQL datetime порт C должен явно восстановить согласованный часовой пояс. Контрактные проверки D находятся в `test_d_contracts.py`.

## Демонстрация настоящего MVP после подключения B/C

1. Зарегистрировать два вымышленных аккаунта, подтвердить email в Mailpit.
2. Кандидат заполнить профиль/контакты, скачать личный PDF.
3. Кандидат принять публикацию, выбрать видимые поля.
4. Пройти реальное тестирование B; работодатель создать компанию/потребность в C.
5. Работодатель открыть рекомендованного кандидата C: alias, выбранные поля и подтверждённые навыки; контактов нет.
6. Отправить приглашение без вакансии: описание, RUB от–до, связь и реальные основания.
7. Кандидат открыть предложение, проверить условия, разрешить передачу контактов этой компании и принять.
8. Работодатель обновить предложение и получить контакты. Другая компания получает 404.
9. На другом предложении выбрать отказ: соответствующего grant нет.
10. Отозвать публикацию: профиль исчезает из выдач; снимок старого предложения сохраняется.
11. Отозвать контактный доступ: endpoint закрывается; повтор accept не восстанавливает grant.

## Контролируемая демонстрация D без B/C

```sh
# Из корня репозитория, сначала зависимости по README
PYTHONPATH=apps/api .venv/bin/pytest apps/api/tests -q
cd apps/web
npm run test:e2e:d
```

Playwright сам поднимает отдельный A/D API и Vite на 8078/8079, применяет миграции, дважды загружает тестовый seed, входит в отдельные contexts кандидата/двух работодателей и проходит публикацию/приглашение/принятие/контакты/отзыв/отказ/PDF. B/C ports здесь строго контролируемые тестовые doubles. Production `app.main` их не импортирует.

Для PostgreSQL заранее создать отдельную БД с именем `_test`, затем:

```sh
D_E2E_DATABASE_URL=postgresql+psycopg://signal:signal-local-only@localhost:54329/signal_d_e2e_test npm run test:e2e:d
```

`fixtures/profiles/scenarios.json` содержит D01–D05 и E01/E02, `tests/seed_d.py` отказывается работать с обычной БД и не создаёт дубликатов. Снимки и PDF теста сохраняются в игнорируемом `test-results/`. Seed не изменяет уже заполненные пользователем строки.

До реальной интеграции нельзя объявлять эти сценарии общим G1/G2. Готовые материалы D передаются как часть документации команды; финальные презентация, размещение и доступ жюри — зона A.
