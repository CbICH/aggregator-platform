# Модуль D: профиль, приватность, приглашения и контакты

D хранит ручное резюме, приватные контакты, профильные согласия, настройки публикации, снимки приглашений, события и права контакта. `candidate_id` равен UUID пользователя кандидата. Категории и результаты тестов принадлежат B; компания, потребность и данные ФСП — C.

## Профиль и PDF

| Метод `/api/v1` | Доступ | Поведение |
|---|---|---|
| `GET /candidate/profile-policy` | Кандидат, включая неподтверждённый email | Версия/текст обработки профиля |
| `GET /candidate/profile` | Тот же | Собственный `CandidateSelf`; пустой черновик без записи в БД |
| `PATCH /candidate/profile` | Тот же + CSRF | Частичное изменение, обязательная `expected_version` |
| `GET /candidate/profile.pdf` | Кандидат с подтверждённым email | Личный PDF сохранённого профиля с действующим согласием обработки |

Первое сохранение требует `processing_consent_accepted=true` и версии `profile-processing-v1`. `null` очищает email/телефон; остальные поля очищаются пустыми строками/списками. Контактный email не меняет адрес входа. Полный профиль требует ФИО, роли, стек и email либо телефон; нулевой стаж допустим. Профиль не принимает client-side владельца, грейд или публикацию. Версия увеличивается при изменении профиля или приватности; устаревшая вкладка получает 409 без частичной записи.

PDF создаётся ReportLab с включёнными Noto Sans (SIL OFL 1.1). Содержит собственные контакты, опыт, стек, навыки B и состояние ФСП C. Длинное резюме переносится на страницы, HTML экранируется, имя загрузки фиксировано. Отдельного публичного/чужого PDF-маршрута нет; ответы `no-store`.

## Приватность и согласия

| Метод | Поведение |
|---|---|
| `GET /candidate/privacy` | Настройки, версия, причины недоступности, история согласий, тексты условий |
| `PATCH /candidate/privacy` | Видимые поля, публикация с отдельным согласием, скрытие, отзыв всех контактных прав |
| `POST /candidate/consents` | Принятие/отзыв публикации; отзыв обработки или контактного разрешения |

Изменения требуют подтверждённого email, CSRF и `expected_version`. Согласие публикации и `publication_enabled` изменяются одним действием. Разрешается заранее принять публикацию до результата тестирования, но в выдачу профиль попадёт только после категории B.

`discoverable = email_verified AND profile_complete AND profile_processing_active AND publication_enabled AND publication_consent_active AND verified_category_exists`.

ФСП не участвует в этом условии. Проверка повторяется при каждом чтении, включая сохранённую подборку. Публичная проекция содержит сгенерированный alias, категорию/доказательства B и выбранные поля: роли, распознанные технологии, стаж. Скрытый стаж/стек/роли — `null`, перечислены в `hidden_fields`. ФИО, свободное резюме, софт-скиллы и контакты приватны. Произвольные technology tags не публикуются; известные технологии перечислены в `PUBLIC_STACK`.

Скрытие профиля останавливает новые чтения/приглашения и сохраняет снимки существующих предложений. Оно не отзывает ранее выданные контакты. `revoke_contact_access=true` отзывает все действующие grants. Повтор прежней команды accept не восстанавливает право. Новое право возникает только при новом явном принятии другого предложения. Отзыв обработки скрывает профиль, отзывает публикацию/контакты, требует нового согласия при сохранении и блокирует PDF.

Пример публикации:

```json
{"expected_version":1,"publication_enabled":true,"publication_consent_accepted":true,"publication_consent_version":"publication-v1","visible_fields":["roles","declared_stack"]}
```

## Приглашения

| Метод | Доступ |
|---|---|
| `GET /employer/invitation-context` | Работодатель с подтверждённым email и компанией C |
| `GET /employer/candidates`, `GET /employer/candidates/{id}` | Только live публичная проекция D |
| `POST /invitations` | Работодатель, CSRF, `Idempotency-Key` |
| `GET /invitations`, `GET /invitations/{id}`, `GET /invitations/{id}/events` | Только кандидат-адресат или работодатель соответствующей компании |
| `POST /invitations/{id}/view` | Только адресат, CSRF |
| `POST /invitations/{id}/decision` | Только адресат, CSRF и версия |
| `GET /employer/candidates/{id}/contacts` | Только компания с активным grant от принятого предложения |

Списки используют `items`, `limit=1..50`, UUID `cursor`/`next_cursor`. GET не меняет статус. UI имеет обновление и следующую страницу.

Компания берётся из `ActorContext`; клиент не передаёт `company_id`. C должен вернуть существующую компанию с непустым названием. Необязательный `need_id` проверяется через `owns_need`. P0 работает с `vacancy_id=null`; непустая вакансия отклоняется как неподдерживаемая P1-функция.

Запрос содержит адресата, описание 20–6000 символов, связь работодателя 3–300 символов, `Salary` и optional evidence refs. Зарплата — целые положительные рубли в месяц gross, `min <= max`, не больше 2147483647. Основания должны существовать в текущей категории B; снимок сохраняет ID/version теста и баллы. Название компании, alias кандидата, категория, основания, описание, зарплата и связь фиксируются при отправке.

```json
{"candidate_id":"10000000-0000-4000-8000-000000000001","description":"Разрабатывайте API для системы заказов.","salary":{"min":120000,"max":160000},"company_contact":"hr@example.com","evidence_refs":["api.idempotency"]}
```

`Idempotency-Key` (8–128 букв/цифр/`_-`) уникален в компании. Повтор с тем же нормализованным payload возвращает то же приглашение; другое содержание даёт 409. Один активный sent/viewed ограничен partial unique index в БД. Лимит новых отправок — 30 на компанию в час; повтор уже сохранённого ключа лимит не расходует.

Переходы: `sent → viewed → accepted | declined`, прямое решение из sent разрешено. Финалы неизменяемы. Повтор того же решения с прежней версией возвращает текущий результат без нового события/grant; противоположный финал даёт 409. На открытом предложении версия проверяется условным UPDATE. Принятие требует явного `contact_consent_accepted=true`, актуальной `contact-transfer-v1`, действующего согласия обработки и контакта в профиле.

```json
{"action":"accept","expected_version":2,"contact_consent_accepted":true,"contact_consent_version":"contact-transfer-v1"}
```

## Транзакции и интеграция

Миграции `0002_d_profiles` и `0003_d_snapshots` следуют за `0001_core`. История D объединена с B/C (`0009_matching_companies`) ревизией `0010_merge_bcd`; после добавления потребностей C общий head — `0012_merge_matching_needs`, соединяющий `0011_assessment_survey_index` и исходную `0010_matching_needs`. Применённые ревизии не переписываются. Таблицы компаний и потребностей C уже существуют; FK D к компании/потребности/вакансии пока не добавлены, ownership проверяется портами. Merge-ревизия не выполняет DDL: таблицы создаются исходными родительскими миграциями. Вакансии остаются P1.

Сервисы выполняют flush; роутер владеет commit/rollback. Профиль используется как общий write-lock при privacy, отправке и решении; затем выполняется атомарный UPDATE приглашения. Это работает на PostgreSQL и SQLite без предположения о SQLite FOR UPDATE. Запись финала, события, согласия и grant атомарна. Audit хранит действие, UUID и request ID без резюме, email или телефона.

Composition root `configure_d(app)` предоставляет реальные `profile_read_factory(db)` и `contact_access_factory(db)` для C/A. `create_app()` также устанавливает `assessment_read_factory=SqlAlchemyAssessmentRead` и `company_read_factory=SqlAlchemyCompanyRead`. Фабрики получают Session текущего запроса:

```python
app.state.assessment_read_factory = lambda db: RealAssessmentRead(db)
app.state.company_read_factory = lambda db: RealCompanyRead(db)
# После реализации API связи и адаптера C:
# app.state.fsp_read_factory = lambda db: RealFspRead(db)
```

B реализует `get_verified(candidate_id)` и возвращает категорию именно этого кандидата. C реализует `get_summary(company_id)`, `owns_need(company_id, need_id)`; `owns_vacancy` предусмотрен портом для P1. D `ProfileRead` имеет `get_public`, `is_discoverable`, `list_public(actor, after, limit)`; Будущий live-подбор C должен читать только разрешённые публичные значения и повторно проверять профиль перед показом сохранённого результата. D `ContactAccess.get` возвращает DTO или None; внешний endpoint дополнительно проверяет роль, email и компанию.

До подтверждения категории B профиль недоступен работодателю. Без компании actor получает `COMPANY_REQUIRED`; после создания компании C отправка работает. `owns_need` проверяет сохранённую `EmployerNeed` и её `company_id`. Рабочие read-порты D не подменяются тестовыми doubles. Отдельная демо-подборка C на `/employer/matching/candidates` читает JSON-фикстуры, а `/employer/candidates` D — живые опубликованные профили. Демо-рейтинг пока не подключён к ProfileRead/AssessmentRead и не предоставляет переход к приглашению конкретного кандидата D.

ФСП UI ожидает API C: `GET /candidate/fsp` → `FspEvidence`; `POST /candidate/fsp-link` с `{"fsp_id":"..."}` и `DELETE /candidate/fsp-link`. C должен подтвердить владение; ввод ID в D не назначает достижение. Доступны четыре состояния: not_linked, linked_empty, linked_with_data, unavailable. Если C отсутствует, UI показывает недоступность и основной путь остаётся доступен. На срезе 9 октября все три маршрута возвращают 404. Новый `DemoFspProvider` обслуживает синтетический рейтинг C и не реализует `FspRead` для D. ТЗ допускает собственные синтетические данные: внешний API ФСП не требуется для MVP, но рабочая привязка ID и согласованный адаптер необходимы.
