## Связь модулей

`create_app()` устанавливает `SqlAlchemyAssessmentRead`, `SqlAlchemyCompanyRead`, `SqlAlchemyFspRead`, `ProfileRead` и `ContactAccess` как фабрики с общей Session запроса. D читает категорию B для публикации/оснований приглашения и компанию C для условий. C читает только текущие публичные D-поля, текущую категорию B и server-side FSP-сигнал. После создания компании сервер сохраняет `users.company_id`; клиент не назначает владельца.

Потребность → live-ranking → сохранённая подборка → приглашение связаны интерфейсом. D повторно проверяет доступность кандидата и ownership потребности. Принятие с согласием создаёт контактный grant; отзыв закрывает его без восстановления повтором. Сохранённые подборки не обходят приватность.

## Доказательства

149 API-тестов на SQLite и PostgreSQL; шесть исходных миграционных состояний SQLite; временная PostgreSQL upgrade/check/downgrade core/upgrade/check; runtime Alembic check. Четыре production Playwright-сценария и отдельный подробный D E2E. Главный сценарий проходит настоящий B, demo-FSP, потребность C, live-ranking/фильтры/историю и приглашения/контакты/отзыв D.

Локальная проверка чтений: 20 параллельных клиентов с одной авторизованной сессией, 120 запросов каталога/ранжирования/сохранённой подборки на 7 видимых профилях, все HTTP 200; p50 317 мс, p95 431 мс. Это измерение небольшого MVP-стенда, а не оценка большой базы или независимых пользователей.
