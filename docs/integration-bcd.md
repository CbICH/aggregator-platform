## Связь модулей

`create_app()` устанавливает реальные `SqlAlchemyAssessmentRead` и `SqlAlchemyCompanyRead` как фабрики с общей Session запроса. D читает подтверждённую категорию B для публикации/оснований приглашения и компанию C для названия/контакта. После создания компании сервер сохраняет `users.company_id`; клиент не назначает себе компанию.

Оба кабинета имеют рабочие ссылки: кандидат — профиль, тест и приглашения; работодатель — компания, опубликованные профили и приглашения. DTO компании в UI берётся из сгенерированного OpenAPI. Схемы/типы объединены и пересозданы.

## Миграции

Две существующие истории сохранены:

```text
0001_core ── 0002_d_profiles ── 0003_d_snapshots ──────────────┐
          └─ 0002_assessment ── … ── 0009_matching_companies ─┤
                                                           └─ 0010_merge_bcd
                                                              └─ 0011_assessment_survey_index
```

`0010_merge_bcd` соединяет heads без удаления таблиц; `0011` добавляет недостающий индекс B. Модель уникальности владельца компании согласована с исходной миграцией C. Запуск использует обычный `alembic upgrade head`; не требуется сбрасывать данные или переписывать применённые ревизии.

## Что ещё нужно от C

В Ananas пока нет сохранённых потребностей, ранжированного подбора/поиска и API привязки ФСП. JSON-фикстуры этих сущностей не являются рабочими endpoints. Список профилей D проверяет live-публикацию, но не заменяет подбор по потребности.

`SqlAlchemyCompanyRead.owns_need` и `owns_vacancy` возвращают False до появления соответствующих таблиц C. Приглашение без потребности работает; переданный неизвестный `need_id` не даёт доступа. ФСП показывает unavailable и не блокирует основной путь кандидата.

Следующая интеграция: таблицы/ownership потребностей C → подбор через публичный `ProfileRead` D и подтверждённый `AssessmentRead` B → `FspRead`/проверка владения ID → полный G1/G2. Существующие snapshots, приватность и контактные grants D должны сохранять текущие правила.
