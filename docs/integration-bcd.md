## Связь модулей

`create_app()` устанавливает реальные `SqlAlchemyAssessmentRead` и `SqlAlchemyCompanyRead` как фабрики с общей Session запроса. D читает подтверждённую категорию B для публикации/оснований приглашения и компанию C для названия/контакта. После создания компании сервер сохраняет `users.company_id`; клиент не назначает себе компанию.

Оба кабинета имеют рабочие ссылки: кандидат — профиль, тест и приглашения; работодатель — компания, опубликованные профили и приглашения. DTO компании в UI берётся из сгенерированного OpenAPI. Схемы/типы объединены и пересозданы.

## Границы текущей интеграции C

Сохранённые потребности C и endpoint ranking добавлены. Потребность принадлежит компании; чужой `need_id` возвращает `404`, а D повторно проверяет ownership через `SqlAlchemyCompanyRead`. Отдельный маршрут `/employer/matching/candidates` показывает ranking по JSON-фикстурам C; D-owned `/employer/candidates` остаётся live-выдачей опубликованных профилей и не конфликтует с демо-подбором.

Ranking C пока не подключён к живому `ProfileRead` D и `AssessmentRead` B: синтетический банк используется только для демонстрации формулы. FspProvider также имеет только Demo-адаптер на фикстурах; адаптер привязки текущей учётной записи к ID и `FspRead` отсутствуют. Внешний API ФСП не требуется ТЗ для MVP, синтетический источник допустим. В C пока нет фильтра стека, истории предыдущих подборок и перехода с рейтинговой карточки к приглашению D.

Независимый аудит по ТЗ подтвердил D01–D08 и основной D10. D09 остаётся частичным: интерфейс связи с ФСП ID есть, но `GET/POST/DELETE /api/v1/candidate/fsp*` в текущем production-приложении возвращают 404. Связать профиль с ФСП ID пока нельзя.

Следующая интеграция: подбор сохранённой потребности через публичный `ProfileRead` D и подтверждённый `AssessmentRead` B → переход к приглашению D → `FspRead`/проверка владения ID → фильтры и сохранение прошлых подборок → полный G1/G2. Существующие snapshots, приватность и контактные grants D должны сохранять текущие правила.
