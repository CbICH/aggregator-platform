# Общие контракты и правила интеграции

Версия проекта контракта: 0.1. Это стартовая спецификация для команды, не готовая OpenAPI-спецификация реализованного приложения. A фиксирует её в первые два часа. Каждый владелец переносит свои методы и схемы в код и OpenAPI; итоговая документация генерируется и сверяется с этим соглашением.

## 1. Базовые типы

| Тип | Правило |
|---|---|
| ID | UUID, создаётся сервером; внешние ID ФСП хранятся отдельно как строки |
| Role | `candidate` или `employer`; роль выдаёт сервер |
| Specialization | `backend`, `qa` для базового плана |
| Grade | `junior`, `middle`, `senior`; числовой порядок хранится в справочнике |
| Category | Стабильный код, например `backend:middle`; присваивается после теста |
| Timestamp | ISO 8601 UTC; UI отображает локальное время |
| Salary | Целые рубли в месяц: `min`, `max`, `currency=RUB`, `period=month`, `tax_basis=gross` |
| Баллы | 0–100, округление для UI до одного знака; сортировка по полному значению |
| Пагинация | `limit` 1–50 и `cursor`; в ответе `items`, `next_cursor` |
| Ошибка | `error.code`, `error.message`, необязательные `error.fields`, `request_id` |

Указание «до вычета налогов» отображается возле зарплаты. Это выбранная единая конвенция MVP; ТЗ требует рубли и диапазон, но не задаёт налоговую базу. Проверка: `0 < min <= max`, целые числа, единственная допустимая валюта RUB. Клиент не может подменять принадлежность компании через `company_id` в теле запроса.

`ActorContext = {user_id, role, email_verified, company_id?}` получает сервер из действующей сессии. Модули не принимают его из клиентского JSON.

## 2. Общие справочники

Справочник содержит `id`, `label`, `active`, `version`. В UI показываются только категории с готовым тестом. Стартовые навыки: `api.behavior`, `api.idempotency`, `data.sql`, `data.boundaries`, `qa.test_design`, `qa.defect_analysis`, `qa.risk_priority`.

Заявленные технологии (`python`, `postgresql`, `javascript` и т. п.) — отдельный справочник стека. Навык `api.idempotency` и технология `python` не являются одним типом сущности. Синонимы используются для разбора текста, но сохраняется нормализованный ID.

Опрос: отрасль, специализация, предполагаемый грейд, роли, стаж. Стаж используется как контекст, не как автоматическое подтверждение грейда. Опрос каждой попытки сохраняется снимком с версией справочника.

## 4. Порты между модулями

Порты — внутренние интерфейсы монолита. Их реальные реализации собирает A. Для тестов каждый порт имеет fake-реализацию с теми же типами.

| Порт | Поставщик | Кто читает | Назначение |
|---|---|---|---|
| `AssessmentRead.get_verified(candidate_id)` | B | C, D | Текущая подтверждённая категория и навыки |
| `ProfileRead.get_public(candidate_id, actor)` | D | C | Только разрешённые структурированные поля |
| `ProfileRead.is_discoverable(candidate_id)` | D | C, D | Согласие публикации и статус профиля |
| `CompanyRead.get_summary(company_id)` | C | D | Название и контакт компании для предложения |
| `FspRead.get_evidence(candidate_id)` | C | D, C | Статус и нормализованные достижения |
| `ContactAccess.get(company_id, candidate_id)` | D | C через защищённый API | Проверка права и выдача контактов |
| `AuthRead.get_actor(session)` | A | Все | Проверенный пользователь и компания |
| `ConsentWrite.record_registration(user_id, version)` | D | A | Фиксация явно принятого согласия при регистрации в той же транзакции |

Для получения списка кандидатов C использует согласованную read-only проекцию опубликованных профилей и подтверждений. Допустим SQL view, созданный общей миграцией; модуль C не получает разрешения писать в таблицы B/D. Самостоятельность модуля не требует HTTP-вызовов внутри одного процесса.

Проекция может собираться запросом без отдельного индексационного сервиса. Проверка актуальной видимости обязательна при чтении; рассинхронизация кеша не должна раскрывать скрытые данные.

## 5. Схемы обмена

### 5.1. Подтверждение категории

```json
{
  "candidate_id": "10000000-0000-4000-8000-000000000001",
  "category_code": "backend:middle",
  "specialization": "backend",
  "verified_grade": "middle",
  "test_score": 86.0,
  "assessment_id": "20000000-0000-4000-8000-000000000001",
  "assessment_version": "backend-middle-v1",
  "assigned_at": "2026-10-05T09:00:00Z",
  "next_change_at": "2027-01-03T09:00:00Z",
  "skills": [
    {"id": "api.idempotency", "score": 90, "source": "assessment"},
    {"id": "data.sql", "score": 84, "source": "assessment"}
  ]
}
```

Пример иллюстративный. Только B создаёт эти данные; поле `verified_grade` отсутствует в запросе редактирования профиля. Клиентская передача такого поля должна отклоняться, а не молча обновлять подтверждение.

### 5.2. Потребность работодателя

```json
{
  "title": "Развитие API сервиса заказов",
  "description": "Нужны обработка повторов и работа с данными",
  "specialization": "backend",
  "grades": ["middle"],
  "declared_stack": ["python", "postgresql"],
  "required_skills": [
    {"id": "api.idempotency", "weight": 2},
    {"id": "data.sql", "weight": 1}
  ],
  "work_format": "remote"
}
```

Вес — положительное число. Сервер нормализует веса при расчёте R. Если подтверждаемых навыков нет, UI предлагает выбрать их; для общего банка применяется формула без R. Скрытая подстановка нулевого R для потребности без навыков не допускается.

`R = sum(weight_i * confirmed_skill_score_i) / sum(weight_i)`. Непроверенный требуемый навык имеет числовой вклад 0 и отдельный флаг `not_assessed`. Учитываются только доказательства текущей категории; данные старых уровней не смешиваются без явного правила.

### 5.3. Кандидат в подборке

```json
{
  "candidate_id": "10000000-0000-4000-8000-000000000001",
  "display_name": "Кандидат 014",
  "category_code": "backend:middle",
  "declared_stack": ["python", "postgresql"],
  "score": 83.9,
  "components": {"test": 86, "relevance": 88, "fsp": 60},
  "reasons": [
    {"code": "GRADE_VERIFIED", "label": "Middle подтверждён тестом"},
    {"code": "SKILL_MATCH", "skill_id": "api.idempotency", "score": 90},
    {"code": "FSP_SIGNAL", "label": "Финалист: демонстрационные данные"}
  ],
  "fsp_status": "linked_with_data",
  "can_invite": true,
  "contacts_available": false
}
```

Расчёт примера: 0,65×86 + 0,25×88 + 0,10×60 = 83,9. `contacts_available` не содержит самих контактов. Даже после выдачи разрешения контакты получаются отдельным защищённым методом; кеш поиска не переносит их между компаниями.

### 5.4. Создание приглашения

```json
{
  "candidate_id": "10000000-0000-4000-8000-000000000001",
  "need_id": "30000000-0000-4000-8000-000000000001",
  "vacancy_id": null,
  "description": "Предлагаем развивать API сервиса заказов",
  "salary": {
    "min": 180000, "max": 230000,
    "currency": "RUB", "period": "month", "tax_basis": "gross"
  },
  "company_contact": "hr@example.test",
  "evidence_refs": ["api.idempotency", "data.sql"]
}
```

`need_id` и `vacancy_id` необязательны; при наличии принадлежат компании из сессии. `company_contact` — способ связи работодателя, видимый кандидату до принятия. `evidence_refs` должны указывать на реально доступные доказательства текущего кандидата; свободная выдуманная причина не превращается в подтверждённый факт.

При создании сервер сохраняет снимок названия компании, условий и выбранных оснований. После отправки условия не редактируются незаметно; в P0 исправление означает новое предложение после завершения предыдущего. Уникальный ключ повторного запроса предотвращает дубли при повторном нажатии.

### 5.5. Ошибка

```json
{
  "error": {
    "code": "GRADE_CHANGE_COOLDOWN",
    "message": "Смена грейда пока недоступна",
    "fields": {"next_change_at": "2027-01-03T09:00:00Z"}
  },
  "request_id": "40000000-0000-4000-8000-000000000001"
}
```

HTTP: 400 — некорректная команда; 401 — нет действующей сессии; 403 — действие запрещено роли; 404 — объект отсутствует или недоступен этому пользователю; 409 — конфликт состояния/ограничение смены; 422 — ошибка полей; 429 — превышен лимит. Тексты ошибок не раскрывают чужие контакты или существование чужого приглашения.

## 7. Автоматы состояний и транзакции

### 7.1. Попытка

`created → in_progress → passed | failed | expired`.

Финальные состояния неизменяемы. `passed` означает успешно пройденный тест, а не автоматически назначенный грейд. Назначение выполняется отдельной командой `/candidate/category/confirm`, с проверкой принадлежности попытки, успешности, актуальности версии и cooldown. Для первоначального подтверждения использовать результаты не старше 7 дней; при превышении срока предложить новый тест и объяснить причину.

На одну специализацию/цель у кандидата не больше одной активной попытки. Создание и финализация защищены транзакцией; сервер рассчитывает deadline. Возобновление открывает текущую попытку, не меняя времени.

### 7.2. Категория

`unverified → provisional_pass → verified` для первичного пути. Провал оставляет `unverified`; кандидат выбирает, что делать дальше. Во время первоначального повышения уже полученное успешное подтверждение сохраняется. Для размещённого кандидата текущая `verified` не исчезает при неуспешной попытке.

Назначение записывает в одной транзакции текущую категорию, историю и `next_change_at = assigned_at + 90 дней`. Блокировка записи кандидата или эквивалентная защита предотвращает две конкурентные смены. Изменение резюме не трогает эту транзакцию.

### 7.3. Приглашение

`sent → viewed → accepted | declined`; также допустим `sent → accepted | declined`, если действие выполнено из уведомления. Только кандидат отмечает просмотр и решение. Работодатель видит статус, но не управляет решением кандидата.

`accepted` и `declined` — финальные состояния P0. Отдельного редактирования отправленного предложения в P0 нет. Повтор той же команды идемпотентен, конфликтующее финальное решение получает 409. Список опрашивается периодически либо обновляется после действий; WebSocket необязателен.

Принятие: проверить владельца → заблокировать запись/проверить version → изменить статус → создать ContactGrant → записать событие → commit. Создание права контакта не должно отставать от принятого статуса или произойти при отклонении.

В MVP ограничить число активных приглашений «компания + кандидат» одним; новое можно создать после завершения предыдущего с серверным лимитом против спама. Ответ повторного запроса с тем же ключом соответствует исходной отправке.

### 7.4. Приватность

`discoverable = email_verified AND profile_complete AND verified_category_exists AND publication_consent_active`.

Публичная карточка доступна только работодателю при `discoverable=true`. Сам кандидат всегда может читать свой профиль. Доступ к контактам: компания из сессии совпадает с ContactGrant и разрешение не отозвано. Принятие приглашения не делает профиль общедоступным всему интернету.

При отзыве публикации новые поиски и сохранённые снимки исключают профиль. Существующие приглашения остаются видны их сторонам с минимальным снимком предложения и статусом. При отзыве разрешения передачи контактов ContactGrant перестаёт действовать; уже полученные работодателем сведения технически не удаляются из его внешних систем автоматически.

## 9. Контрактные проверки перед слиянием

1. DTO проходят общую схему; поля `null` и отсутствующие поля трактуются одинаково.
2. Все timestamps содержат часовой пояс; Salary и enum не представлены свободным текстом.
3. Публичные ответы не содержат email, phone, приватное резюме, ссылку на приватный PDF или секреты тестирования.
4. Приглашение без вакансии создаётся; отсутствие зарплаты даёт ошибку.
5. Один и тот же результат теста в B, карточке C и кабинете D показывает один грейд.
6. Реальная реализация порта и fake проходят одни и те же ключевые примеры.
7. Миграции применяются на пустой базе; seed запускается повторно без дубликатов.
8. OpenAPI включает фактические ответы и ошибки; клиентская схема обновлена вместе с серверной.

Контракт 0.1 достаточно узок, чтобы три функциональных участника начали работу независимо. Дополнения возможны, но должны иметь конкретного потребителя и не откладывать интеграцию основного пути.
