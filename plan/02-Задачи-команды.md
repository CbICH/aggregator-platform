# Задачи четырёх участников

Этот файл — рабочий backlog к плану «ФСП Сигнал». A/B/C/D заменить именами. Оценки — ориентировочные часы сосредоточенной работы с резервом; они зависят от опыта команды. Временные интервалы основного плана обозначают окна выполнения, а не непрерывную занятость.

Каждую строку перенести в задачу трекера с полями: владелец, P0/P1, ожидаемый результат, критерий приёмки, зависимости, ссылка на PR, доказательство проверки. Одна задача — один наблюдаемый результат. Все позиции из таблиц ниже имеют приоритет P0, если не сказано иное.

## A. Координатор, общий каркас и интеграция

**Цель:** предоставить команде устойчивые договорённости и довести соединённый продукт до сдачи. A не становится единственным тестировщиком и автором всей документации.

| ID | Задача | Оценка | Готово, когда |
|---|---|---:|---|
| A01 | Зафиксировать scope, владельцев, DTO, справочники и график | 1,5 ч | Файл контрактов принят командой; у каждого есть фикстуры и маршрут |
| A02 | Создать каркас web/api, БД, миграции, конфигурацию | 2 ч | Все запускают одинаковое окружение и видят healthcheck |
| A03 | Реализовать регистрацию, вход, выход, email-подтверждение | 3,5 ч | Письмо доставляется; токен одноразовый; повтор и истечение проверены |
| A04 | Общие роли, сессия, ошибки, журнал событий, ограничение запросов | 1,5 ч | Модули получают проверенный ActorContext; роль клиента не считается доверенной |
| A05 | Общая навигация, формы и базовые UI-компоненты | 1 ч | B/C/D подключают страницы без редактирования общего каркаса |
| A06 | CI, compose, первый деплой, настройка SMTP | 2 ч | Чистая сборка проходит; публичная или резервная локальная среда доступна |
| A07 | Интеграция G1/G2 и исправление общих дефектов | 3 ч | Основной путь проходит через реальные сервисы и БД |
| A08 | Сквозной тест, чистый запуск, нагрузка, общие проверки доступа | 2,5 ч | Есть отчёты и нет критических дефектов P0 |
| A09 | Сборка документации, зависимостей и ссылок | 1,5 ч | Итоговый doc/pdf содержит все восемь разделов ТЗ |
| A10 | Презентация, демо, видео, промежуточная и финальная сдача | 2,5 ч | Материалы открываются, ссылки доступны, демо отрепетировано |
| A11 | Резерв на координацию и неисправности | 3 ч | Расходуется только на критический путь |

**Итого: 24 часа.** Регулярные синхронизации по 10 минут каждые 3–4 часа входят в резерв. Если инфраструктура отнимает больше двух дополнительных часов, сокращаем P1 и заранее готовим локальную демонстрацию.

Первая поставка A к двум часам: структура репозитория, шаблон маршрута, формат ошибок, `ActorContext`, пустые сервисные порты, инструкция запуска. Сама авторизация может завершаться позже; тестовые зависимости дают остальным возможность работать.

Владеет: `core`, `infra`, общей навигацией, CI, сборкой API, общей цепочкой миграций. Не меняет доменную логику B/C/D без автора; интеграционные исправления делает совместно с владельцем.

Приёмка A: новый участник по README разворачивает систему, создаёт пользователя, получает письмо, проходит основной сценарий; на публичной среде отсутствует тестовый вход в обход авторизации.

## B. Опрос, тестирование и подтверждённый грейд

**Цель:** независимо выдавать достоверный в рамках прототипа результат, на котором строится поиск.

| ID | Задача | Оценка | Готово, когда |
|---|---|---:|---|
| B01 | Справочник направлений, грейдов, навыков; фикстуры результата | 1 ч | Есть 6 категорий и однозначные идентификаторы |
| B02 | Опрос и выбор заявленного грейда | 1,5 ч | Данные валидируются и сохраняются, обход обязательных полей невозможен |
| B03 | Жизненный цикл попытки, серверное время, черновик и submit | 2,5 ч | Ответ после срока не принимается; повтор submit не начисляет баллы заново |
| B04 | Первое семейство: генератор, эталон и оценка | 2 ч | Для одной категории проходит полный путь без ручной выдачи результата |
| B05 | Расширить до 18 шаблонов по единой структуре | 5 ч | Все заявленные категории имеют 3 работающих семейства |
| B06 | Экран теста, результат, объяснение по навыкам | 2 ч | Пользователь видит, что проверялось и каков результат |
| B07 | Назначение категории, история, повторные попытки, 90 дней | 2,5 ч | Все переходы проверены; провал не понижает текущую категорию |
| B08 | Генеративные проверки, граничные ответы, перенос ответов | 2 ч | Есть отчёт по 100 вариантам каждого шаблона и тестам порогов |
| B09 | Пилот с людьми и сравнение с ручной оценкой | 2 ч | Есть сырые результаты, размер выборки, ограничения и расчёты |
| B10 | Интеграция и документация тестирования | 1,5 ч | C получает подтверждения по контракту; раздел docs совпадает с кодом |
| B11 | Резерв на сложность заданий и дефекты | 3 ч | Используется на исправление качества, затем на сокращение объёма |

**Итого: 25 часов.** B05 — наиболее рискованная оценка: это компактные структурированные шаблоны, не полноценные задачи с произвольным исполнением кода. C помогает сформулировать рабочие ситуации и требования; A организует добровольцев для пилота. При отставании сокращается число специализаций по правилам основного плана, а не проверка корректности.

Входы: `ActorContext`, справочник навыков, три нормализованных описания потребностей C. До готовности C используются согласованные JSON-фикстуры. B не зависит от готовности экранов профиля D.

Выходы: `AssessmentSummary`, `VerifiedCategory`, `SkillEvidence`, история попыток, дата разрешённой смены. Персональные контакты B не нужны.

Первая поставка к шестому часу: один полный тест с результатом и фикстурами других состояний. К G1 — реальная запись подтверждения в БД. До G2 — все объявленные категории, история и ограничения.

Обязательные отрицательные проверки:

- Чужой пользователь не получает попытку и не отправляет ответы за владельца.
- Заявленный Senior при провале не превращается в подтверждённый Junior автоматически.
- Редактирование резюме и клиентского JSON не изменяет грейд.
- Две одновременные команды назначения категории не обходят 90 дней.
- Эталонные ответы, внутренний seed и рубрика со скрытыми проверками не выдаются клиенту.
- Перезагрузка страницы не обнуляет серверный таймер и не создаёт лишнюю попытку.

P1 B: движок коротких задач и отдельный сигнал актуальности. Расписание и экран включаются только при завершённом P0.

## C. Кабинет работодателя, подбор и ФСП

**Цель:** работодатель получает объяснимую подборку по задачам, а данные ФСП добавляют проверяемый контекст.

| ID | Задача | Оценка | Готово, когда |
|---|---|---:|---|
| C01 | Фикстуры компании, потребности, выдачи и ФСП | 1 ч | Можно собрать поиск без живых B/D |
| C02 | Профиль компании и форма потребности | 2 ч | Все поля ТЗ сохраняются, компания берётся из сессии |
| C03 | Три описания вакансий → словарь навыков → подтверждение формы | 1,5 ч | Видна связь текста, структурированных навыков и теста |
| C04 | Категории, фильтры, запросы к реальной БД | 3 ч | Все фильтры ТЗ работают; неподтверждённые профили не попадают в выдачу |
| C05 | Формула рейтинга, причины, происхождение навыков | 2 ч | Позицию можно пересчитать, объяснение не противоречит баллам |
| C06 | UI выдачи и карточки кандидата | 2,5 ч | Есть загрузка, пустой результат, ошибки, кнопка приглашения |
| C07 | Снимки поиска, уточнение, возврат, избранное | 1,5 ч | Исходная подборка сохраняется, скрытые профили не возвращаются |
| C08 | FspProvider и демонстрационные состояния | 2 ч | Связь подтверждается адаптером; нет ФСП и недоступность различаются |
| C09 | Генератор данных, разметка пар, baseline и метрики | 3 ч | Результаты воспроизводимы, контрольная часть не использовалась для настройки |
| C10 | Интеграция и документация подбора/ФСП/ATS | 1,5 ч | Реальные данные B/D подключены; архитектурные границы описаны |
| C11 | Резерв на выдачу и качество данных | 3 ч | Исправлены провалы главного сценария |

**Итого: 23 часа.** Вторым оценщиком пар в C09 выступает A или D. Чтобы избежать очереди на просмотр, C готовит короткие карточки с доказательствами заранее.

Входы: безопасные профили от D, подтверждённые категории и навыки B, контекст компании A. Выходы: `CompanySummary`, `EmployerNeed`, `SearchSnapshot`, `CandidateMatch`, `FspEvidence`. C не читает приватную таблицу контактов.

Первая поставка к шестому часу: форма потребности и поиск на фикстурах; к G1 — реальная категория B, реальный профиль D и переход к приглашению. Если D ещё не готов, кнопка открывает экран с контрактным candidate ID, а не заставляет C реализовывать чужой модуль.

Обязательные отрицательные проверки:

- Изменение потребности чужой компании запрещено.
- Самоописанный стек не создаёт подтверждённый навык и не меняет категорию.
- Кандидат без ФСП находится, если не включён явный фильтр «только с ФСП».
- Ошибка адаптера не изображается как достоверное отсутствие достижений.
- Снимок поиска не раскрывает профиль после отзыва публикации.
- Изменение фильтра не стирает предыдущую подборку.

P1 C: публикация и редактирование вакансий, общий список, адаптация поиска; создание короткой задачи работодателя. P2: схема верификации компаний и внешней ATS.

## D. Профиль, согласия, приглашения и контакт

**Цель:** кандидат управляет своим профилем и доступом, работодатель может отправить и отследить предложение.

| ID | Задача | Оценка | Готово, когда |
|---|---|---:|---|
| D01 | Фикстуры профиля, приглашения и состояний доступа | 1 ч | C может читать безопасный профиль, D — тестировать предложение |
| D02 | Форма резюме и профиль кандидата | 2,5 ч | Сохраняются ФИО, контакты, стек, роли, стаж, софт-скиллы |
| D03 | Согласия, настройки полей, публикация/скрытие | 2,5 ч | Настройки влияют на серверный ответ и поиск |
| D04 | Публичная проекция и отдельный доступ к контактам | 2 ч | API не выдаёт контакт до разрешения конкретной компании |
| D05 | Создание приглашения и обязательная зарплата | 2 ч | Работает без vacancy_id, все поля валидируются |
| D06 | Принятие/отказ, просмотр, идемпотентность, журнал | 2,5 ч | Корректные переходы, гонки и повторные запросы обработаны |
| D07 | Списки приглашений для обеих ролей | 2 ч | Статусы согласованы; есть пустые состояния и обновление |
| D08 | Генерация PDF-профиля | 1,5 ч | Скачивается только владельцем; кириллица и длинный текст не ломаются |
| D09 | UI ФСП-связи и общая карточка статуса кандидата | 1 ч | Используются API C/B, не дублируется их логика |
| D10 | Негативные проверки доступа, E2E и документация | 2,5 ч | Нет утечки по чужим ID, через PDF или список приглашений |
| D11 | Резерв на UX и интеграцию | 3 ч | Основной сценарий устойчив |

**Итого: 22,5 часа.** Для P0 PDF доступен самому кандидату. Экспорт работодателю не требуется: если его добавлять, он обязан использовать отдельную безопасную проекцию и проверку права контакта.

Входы: `ActorContext`, категория B, компания C, ФСП-статус C. Выходы: `CandidatePublic`, `CandidateSelf`, `Invitation`, `ContactGrant`. Предварительная разработка использует фикстуры B/C.

Первая поставка к шестому часу: форма профиля и переходы приглашения на фикстурах. К G1 — реальное принятие в транзакции и раскрытие контактов. Согласия и публикация включены до первого показа реального профиля в общей выдаче.

Обязательные отрицательные проверки:

- Работодатель не может принять приглашение вместо кандидата.
- Кандидат не может поменять адресата, компанию и сумму предложения.
- Отклонение не создаёт право контакта.
- Принятие компании A не даёт доступ компании B.
- Конкурирующие принятие и отказ не создают противоречивое состояние.
- Пустая зарплата, валюта не RUB и `min > max` возвращают ошибку.
- PDF владельца не скачивается другим кандидатом или работодателем по прямому URL.

P1 D: самостоятельные отклики на вакансии C, статусы, отзыв отклика по выбранной политике, создание права контакта при добровольной отправке. Перед отправкой UI ясно сообщает о раскрытии контактов указанной компании.

## Общие правила готовности задачи

Задача считается завершённой, когда код слит в общую ветку, проверены успешный сценарий и существенные ошибки, добавлены request/response/error-схемы, обновлены фикстуры и краткая документация. Скриншот интерфейса без работающей серверной логики не закрывает задачу.

Для внутренних функций проверяем поведение, влияющее на ТЗ: грейд, фильтры, разрешения, деньги, статусы. Не расходуем время на тесты каждого декоративного компонента.

Порядок интеграции:

1. A подключает маршруты и зависимости; владельцы проверяют работу своих модулей в общем приложении.
2. B отдаёт подтверждение, D — безопасный профиль; C заменяет фикстуры реальными портами.
3. C открывает создание приглашения D с ID кандидата и потребности.
4. D принимает приглашение, выдаёт право контакта, C обновляет карточку.
5. Все проходят путь под разными аккаунтами, A фиксирует G1/G2.

При конфликте общего файла побеждает согласованный контракт, а не последняя слитая ветка. При дефекте соседнего модуля создаётся минимальный воспроизводимый пример и фикстура; никто не переписывает чужую реализацию целиком.
